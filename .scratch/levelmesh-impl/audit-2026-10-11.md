# Levelmesh audit — spec, tickets, pipeline (2026-10-11)

Scope: `.scratch/levelmesh-rendering/spec.md` (§1–§11 + ADRs 0001–0004 as cited), `.scratch/levelmesh-impl/map.md`
and tickets 01–13, and the code on branch `agent-levelmesh` @ `7dac2c38`:
`src/common/rendering/levelmesh{,_state,_frame}.{h,cpp}`, `gl/gl_levelmesh.*`, `gl/gl_framebuffer.cpp`
(`DrawLevelMesh`, `UploadLevelMeshSlot`), `gl/gl_renderstate.cpp`, `hwrenderer/scene/hw_drawinfo.cpp`
(`RenderScene`), `hw_drawlist.cpp`, `d_main.cpp` (`D_Render`), `maploader.cpp` (build site),
`doom_levelmesh.cpp`, `wadsrc/static/shaders/glsl/levelmesh.{vp,fp}` + `levelmesh_light.glsl`, and the
perf kit results in `tools/abtest/results/baseline.{md,json}`.

The audit question: the whole point of the levelmesh is a large rendering-performance win. Does the
current spec + implementation deliver that, and if not, what has to change?
No code was changed for this audit.

Severity tags: **[CRIT]** defeats the purpose / invalidates a premise · **[HIGH]** major perf or
correctness problem · **[MED]** real but bounded · **[LOW]** cleanup / hygiene. "Verified" means
read in code or data; "inferred" means reasoned from code and still needs a measurement.

---

## 0. Verdict (TL;DR)

1. **The current levelmesh path does more work than the classic path, not less.** Nothing on the
   levelmesh path skips the classic scene build: `CreateScene` (BSP walk, clipper, `HWWall::Process`,
   `HWFlat`, per-frame vertex generation, the job pool, sprites, portals) runs in full. The mesh draw
   only *replaces the draw of* the plain/masked wall and flat lists. On top of that the frame adds a
   full sector snapshot, a CPU repack, a multi-MB upload, two cull walks, and a whole-frustum GPU
   draw with no occlusion culling. As built, the path can only be slower. (§2.1)
2. **The perf baseline does not measure rendering.** The baseline medians show **0–34 walls, 0–32
   flats, 0 sprites per frame**. SOS_Boom MAP32, the "scale payoff" map, renders a median of
   **0 walls / 0 flats / 0 sprites** (`wl/fl/sp` in `baseline.json`). The synthetic noclip spiral
   cameras are mostly looking at nothing. The 0.3–0.8 ms "classic" frame times are
   fixed overhead: present, post-process, 2D. Both perf bars are anchored to empty frames. The
   "≤ 50 % of classic on SOS MAP32" bar cannot be met and doesn't mean anything: classic
   render-CPU there is 0.027 ms of a 0.468 ms frame. (§1)
3. **The spec has no spatial culling or occlusion story for the main view.** The only culling unit
   is a (region, texture) group whose AABB is the union of every surface of that texture in the
   region. A non-portal map is one region, so most groups span the whole map and frustum culling
   rejects almost nothing. The classic path gets near-PVS occlusion for free from the BSP clipper.
   The levelmesh path gives that up and keeps none of it. On big maps (myhouse MAP01: 166 k lines,
   9.8 k 3D floors, 410 portals) the GPU would draw most of the level every frame. Each vertex
   runs a ~40–60-texel-fetch vertex shader, and the program always contains `discard`, which
   defeats early-Z. (§2.2, §4)
4. **Parity-first locked the architecture before any perf evidence existed.** The zero-tolerance
   pixel A/B (ADR 0004) and the "bit-exact port" mandate caused these choices: per-vertex
   evaluation of per-surface state, a forked `main.fp`, a ~1600-line re-implementation of
   `HWWall`/`HWFlat` logic in the builder, and the static↔dynamic re-bake lifecycle. Performance
   is first measured in ticket 11, the last ticket. (§3)
5. **The partition code has a real bug.** The region flood-fill only walks front→back
   (`levelmesh.cpp:164-175`). That likely explains "9,905 regions for 9,907 sectors" on SOS MAP32
   (commit `1f7c6011`). Load-time build loops are O(regions × segs/subsectors/surfaces), which is
   billions of iterations on that map. They run on **every** map load even with
   `gl_uselevelmesh 0`. (§5)

**Recommendation:** stop feature tickets (04–11) and run a measurement spike first (§7). The likely
outcome is a re-architecture. The front-runner is to keep the BSP/clipper for visibility and drop
everything per-surface: draw the visible static ranges from the baked mesh in a few batched draws.
On Vulkan / GL 4.6, GPU-driven culling could come later. Details are in §6.

## 1. The performance premise and its measurement

### 1.1 [CRIT] Baseline frames are (nearly) empty — verified
`tools/abtest/results/baseline.json`, median per frame (gl33):

| map | total ms | r (RenderView) | bsp | walls `wl` | flats `fl` | sprites `sp` |
|---|---|---|---|---|---|---|
| SOS_MAP32 (61,623 lines) | 0.468 | 0.027 | 0.003 | **0** | **0** | **0** |
| SOS_MAP12 | 0.455 | 0.028 | 0.004 | 0 | 1 | 0 |
| PLANISF_MAP01 (37,265 lines) | 0.572 | 0.057 | 0.007 | 14 | 5 | 24 |
| MYHOUSE_MAP01 (165,922 lines) | 0.821 | 0.203 | 0.083 | 6 | 3 | 0 |
| MYHOUSE_20PAM | 0.528 | 0.069 | 0.010 | 34 | 32 | 0 |
| DOOM2_MAP01 | 0.464 | 0.035 | 0.004 | 6 | 4 | 0 |

- A median frame on the slaughter map draws zero walls. The synthetic `make_demo.py` spiral
  (noclip2, `-nomonsters`) puts the camera somewhere it sees nothing: outside the map, inside the
  void, or facing a single wall. The data can't tell these apart; spot-check frames to confirm.
- `fin` (swap + sync wait) dominates every frame at 0.2–0.35 ms. `r` is 3–25 %. The levelmesh can
  only shrink the CPU scene-build share, so on these frames there is nothing to win.
- **The bars in spec §9/§10 are therefore invalid:** "levelmesh ≤ classic × 1.05" compares two
  empty frames, and "SOS MAP32 ≤ 50 % of classic" would need the levelmesh to halve present/2D
  overhead.
- `-nomonsters` removes the dominant real cost of slaughter maps (actors, sprites, sight checks).
  The levelmesh doesn't touch sprites at all: they stay on the classic batch path. So SOS_Boom is
  not a levelmesh showcase even with real cameras, unless the bar is about geometry only.

### 1.2 [HIGH] Perflog coverage looks inconsistent — inferred, verify
Frame counts vs. run duration don't match the medians. MYHOUSE_MAP01 logs 19,819 frames over
2600 tics (~74 s of demo, ~80–90 s per run), which is ≥ 3.7 ms per frame on average. The logged
`total` median is 0.82 ms. Load time and long tails may explain part of the gap, but `FrameCycles`
may also miss parts of the frame (the sim tick, `I_StartTic`, the wipe). Before using any of these
numbers, check that `total` covers the whole wall-clock frame.

### 1.3 [HIGH] Medians are the wrong statistic for this feature
The classic renderer's problem cases are worst-case vistas: big open views of detailed maps,
portal-heavy views, many 3D floors in view. Those show up in p95/p99/max and in fixed-vantage
stress views, not in the median of a wandering camera. The spec bars are median-only (D9/D10).

### 1.4 [HIGH] The levelmesh frame-build metric (`lmfb`/`lmdc`) measures the wrong cull
`lm_drawentries` comes from the `D_Render` pre-cull (player origin, un-interpolated, ignores
camera actors). `RenderScene` then re-culls with the real matrices (`hw_drawinfo.cpp:575-581`), so
the logged `lmdc` is not the drawn count, and `lmfb` leaves out the second cull and the draw.

## 2. Architecture: where the performance should come from, and why it doesn't

### 2.1 [CRIT] The classic scene build still runs in full on the levelmesh path — verified
- `D_Render` (`d_main.cpp:614-626`) adds PackSnapshot + cull + upload, then calls `action()` →
  `RenderView` → `ProcessScene` → `CreateScene` **unchanged**. No `useLevelMesh` check exists
  anywhere in `hw_bsp.cpp`, `hw_walls.cpp`, `hw_flats.cpp`, or `hw_drawinfo.cpp::CreateScene`.
- `RenderScene` (`hw_drawinfo.cpp:575-592`) skips only the *draw* of `GLDL_PLAIN*/MASKED*`. It
  then walks those lists again to pick out polyobject walls and hack flats
  (`DrawPolyobjWalls`/`DrawHackFlats`, `hw_drawlist.cpp:859-907`).
- Every `HWWall::Process` / `HWFlat::ProcessSector` still runs. Their vertices are still written
  into the per-frame vertex buffer, then thrown away.
- map.md records this as a decision: "Classic lists keep the view-dependent / moving pieces: on
  the levelmesh path the BSP walk still runs". That turns the levelmesh into an *overlay* on the
  classic path instead of a replacement. The spec's component-fate table (§7) says `hw_bsp`,
  `hw_walls`, `hw_flats` are "removed from frame", and the implementation contradicts it.
- **Why it can't simply be switched off:** sky (sky portals from the walk), translucent walls and
  flats, missing-texture/flood fills, polyobjects, sprites, decals, portals, exposure flags, and
  dither all come from the walk today. Each one is a separate ticket's worth of work (06/07/08/13
  plus ones nobody has written: translucent geometry, polyobjects, hack fills, sprite gather).
  Until **all** of them are done, the levelmesh path can't be faster. The plan puts that point at
  the very end of the critical path.

### 2.2 [CRIT] No occlusion culling for the main view; the culling unit is too coarse — verified + inferred
- The culling unit is a `LevelMeshTexRange` = (region, texture, drawState), with the AABB being the
  **union over all surfaces of that texture in the region** (`levelmesh.cpp:1514-1545`).
- Spec §5 makes a region a portal-connected component. Without the partition bug (§5.1), a
  non-portal map has one region, so each texture's AABB covers most of the map. With the z-extent
  forced to ±32768 (`levelmesh_frame.cpp:84-116`), frustum culling rejects almost nothing.
  **Effectively the whole level is drawn every frame.**
- The classic BSP + clipper is a precise front-to-back occluder: only the potentially visible
  subsectors are emitted. The spec gives this up with no replacement:
  - no spatial chunking,
  - no Hi-Z / occlusion queries for the main view (queries exist only for portal windows),
  - no PVS / portal-cell visibility.
- Helion gets away with whole-level brute force because its target maps are small. The acceptance
  set here is myhouse MAP01 / planisf / SOS, which is exactly where brute force fails.
- With the actual buggy partition (≈ one region per sector), the culling is finer, but draw
  submissions explode instead (§4.4). **Either way the culling model is wrong:** portal topology
  and spatial culling granularity are two separate concerns, and the spec conflates them in one
  "region" concept.

### 2.3 [HIGH] The spec never sizes the GPU side of "draw the level"
§9/§10 only discuss CPU windows and upload bandwidth. Nothing estimates vertex count × VS cost or
fill/overdraw for the full-level draw, even though the design moves per-surface work onto every
vertex (§4.1) and loses early-Z (§4.3). Without a culling story, the GPU cost grows with *level*
size, while the classic GPU cost grows with *visible* size. That reverses the scaling the feature
is supposed to deliver.

### 2.4 [HIGH] The "draw everything, shade per vertex" model fights the hard cases
- **Portals (§5 of spec):** each portal view draws its target region's sub-ranges. Today that
  means the whole level again, because portal views call the same `RenderScene` → `DrawLevelMesh`
  with no region scoping. myhouse MAP01 has 410 line portals. The spec's region scoping depends on
  the partition being correct *and* small, and portal regions on that map can be large.
- **3D floors (§6 band split):** each band repeats the wall's IBO range. Bands are per-wall and
  get drawn wherever the wall's group survives the frustum test, so on 9.8 k-3D-floor maps the
  repeated-index cost multiplies.
- **Dynamic lights (ticket 12):** clustered forward+ is the right direction, but on GL33 it needs
  a CPU binner + texel buffers, and it adds per-pixel cost to every surface. Classic per-surface
  light lists only touch lit surfaces.

### 2.5 [MED] The render worker (Vulkan, §7) is complexity for little gain
- The spec itself admits the worker only moves upload + submit off the game thread. Those costs
  exist because the design does full-frame copies (ADR 0003). With dirty-only or persistently
  mapped updates they would be small.
- With 2 slots it adds up to one frame of latency. It also adds a new thread-ownership model
  (frozen slots, fences, back-pressure) to an engine with no HW render thread today.
- The perf case is unproven. Defer it until measurements show issue cost on the critical path.

### 2.6 [MED] Portal visibility via 1-frame-late queries + velocity prediction (§5)
- **Contradicts zero-tolerance A/B:** a moving-camera demo will show portal pop-in diffs, which
  ADR 0004 says only z-fighting may excuse.
- **Simpler and same-frame:** draw the window polygons with queries and gate each portal's draw
  with **conditional rendering**: `glBeginConditionalRender` is core GL 3.0, and Vulkan has
  `VK_EXT_conditional_rendering`. That removes the prediction, the staleness, and the CPU
  readback. It doesn't gate CPU-side work (sprite gather), but that is cheap.

## 3. Spec-level design problems (beyond perf)

### 3.1 [HIGH] Parity-first, perf-last plan
- **The perf gate comes last.** Eleven tickets lock layouts, protocols, and threading before any
  perf prototype. The first perf gate is ticket 11. A measurement spike (§7) should have been
  ticket 01b.
- **Zero tolerance outlaws every perf-motivated approximation.** The A/B policy has already been
  bent three times: the z-fight allowlist, ticket 12 (clustered lights may select differently at
  edges), and §5's accepted portal latency. Write down explicitly which deltas are acceptable
  *for performance*, instead of discovering them ticket by ticket.

### 3.2 [HIGH] Duplicate implementation of classic geometry logic
- `levelmesh.cpp` re-implements `HWWall::Process`, `DoTexture`, `DoMidTexture`,
  `SetWallCoordinates`, `CheckTexturePosition`, the gl_seamless splits, `CreateVerticesForSubsector`,
  and more (commit `766f390f`). The draw-pass diagnosis log is mostly bugs from imperfect copies.
- From now on, every classic fix has to be made twice.
- **Alternative: bake by running the classic code.** At load, run `HWWall::Process` /
  `HWFlat::ProcessSector` for every seg/subsector, with a capturing `HWWallDispatcher`/vertex sink
  that records the emitted vertices into the pool. The geometry then matches the classic path by
  construction, and its logic is maintained in one place. A small number of view-dependent
  branches (sky, portal walls, `isculled`, hack fills) need flags. Those branches are already
  excluded from the mesh today.

### 3.3 [HIGH] The same forking applies to shading
- `levelmesh.fp` is a 1033-line copy of `main.fp` with a `#define` block on top. It will diverge.
- The levelmesh is an *effect* shader (`hw_shaderpatcher.cpp:311`) with hard-wired
  `func_normal`/`material_normal`. That rules out every material shader variant (warp, PBR,
  specular, brightmap/glow layer variants, user shaders), as ticket 13 notes. It also forces a
  single always-alpha-tested variant (§4.3).
- **Fix:** make "levelmesh" a vertex-stage variant axis of the existing shader matrix, the same way
  `FShaderManager` keys main shaders, instead of an effect. Use a shared fragment include with the
  redirect block, not a copied file.

### 3.4 [HIGH] The static↔dynamic lifecycle (§3/§4, ticket 04) solves a non-problem
- The vertex shader already fetches the front sector's floor/ceiling planes for **every** vertex
  (glow planes: `pFF`/`pFC`, `levelmesh.vp` steps 3 and 10). It also fetches the light sector
  record.
- Once those records are in registers, evaluating `ZatPoint` costs about 4 FLOPs. Baking z and
  re-baking at rest saves nothing on the GPU.
- It costs:
  - the dual-purpose vertex slot,
  - first-movement flag flips with vertex sub-uploads,
  - the "write to all ring slots" hazard rule,
  - the N=2 settle detector,
  - re-bake patches,
  - two code paths in the VS,
  - and an entire ticket (04).
- **Simplification:** make every plane-bound vertex plane-tracked (store offsets, always warp).
  The only argument for baking is bit-exactness of baked z vs `ZatPoint` in float32, which is the
  parity mandate again (§3.1).

### 3.5 [HIGH] ADR 0003 (full per-frame copy) is sized for 60 fps, but the bar is measured uncapped
- The spec's "≈ 4.8 MB/frame ≈ 288 MB/s at 60 fps" assumes 60 fps. The perf protocol runs
  uncapped at hundreds to thousands of fps.
- **GL actually uploads 160 B per sector, not 96:** 40 floats after repack (§4.2). On myhouse
  MAP01 that is 35,853 × 160 B = **5.7 MB/frame**: about 0.8 GB/s at 144 fps, or ~7 GB/s at the
  classic's ~1200 fps baseline. It also costs a full CPU pack + repack every frame.
- The justification ("flicker lights dirty many sectors") holds for small maps. On large maps the
  dirty fraction is tiny. ADR 0003 traded perf for A/B determinism, but dirty tracking is just as
  deterministic: same inputs, same writes.
- **Recommendation:** dirty-sector tracking, or pack only changed records into a persistent-mapped
  buffer on Vulkan / GL4.4+, with a full refresh on level load.

### 3.6 [MED] Factual errors in the spec that shaped the design
- **"GLSL 330 has no float↔uint bit-cast" (handoff + `levelmesh.vp` header) is false.**
  `floatBitsToUint`/`uintBitsToFloat` are core in GLSL 3.30. Integer texture buffers
  (`usamplerBuffer`, `GL_RGBA32UI`) are core since GL 3.1. `glVertexAttribIPointer` is core GL 3.0.
  The float-encoding scheme is unnecessary, and so is the per-frame CPU repack. The packed C++
  records could be uploaded verbatim. Side effects of the float encoding:
  - a float sentinel for `LM_PLANEREF_NONE`,
  - `surfaceIndex*4+corner` packed into a float and limited to 2^24,
  - a 64 B surface record inflated to 96 B,
  - a 96 B sector record inflated to 160 B.
- **"GL persistent-mapped" ring (§4/§7):** persistent mapping needs `ARB_buffer_storage` (GL 4.4),
  not GL 3.3. The implementation uses `glBufferSubData`. That makes the slot ring in GL pointless,
  since the driver already orphans or synchronizes implicitly.
- **"≈12 vec4 promoted varyings, inside GL33 limits" (§6):** these come *on top of* the ~9–10 vec4
  standard varyings, for ~16–17 vec4 / 64–68 components. That's over the GL 3.3 guaranteed minimum
  of 60 `MAX_VARYING_COMPONENTS`. Desktop drivers allow 128, but the claim is wrong, and the
  varyings are mostly per-surface constants interpolated as smooth.
- **Memory budget (§3):** "~64–128 MB surface records" for a typical level. Measured: 159 k
  surfaces × 64 B ≈ 10 MB on SOS MAP32. The estimate is off by 10×, which also suggests nobody
  modeled draw counts.
- **§6 `uLightIndex = 0`:** already found false (ticket 12).
- **§3 texture swap = one record sub-upload:** already found false (ticket 13). The shader never
  reads `textureIndex`, and the material binds per group.

### 3.7 [MED] Texture-grouped IBO ranges conflict with every runtime texture change
- **Root cause:** per-(region, texture) IBO spans need a regroup or IBO rewrite whenever any
  surface changes texture (switches, doors, ACS). That follows from GL33-first. With texture arrays
  (GL 3.0 core) or bindless/descriptor indexing (Vulkan), a texture becomes a per-surface record
  field. Swaps then really are one sub-upload, draw counts collapse, and grouping by texture
  becomes unnecessary.
- **GL33-first constrains the perf path:** it rules out MDI (GL 4.3), SSBOs (4.3), compute,
  persistent mapping (4.4), and bindless. Those are exactly the tools that make a static levelmesh
  fast. Reconsider whether the *performance* path should target Vulkan (+ GL 4.5/4.6 where
  available) and leave GL33 users on the classic path.

### 3.8 [MED] Scope and verification burden vs payoff
- The acceptance load is heavy: 104 A/B combinations with two launches each, plus a cvar sweep,
  a half-day soak, a full-parity mandate (ADR 0001), and two complete backends.
- Meanwhile the perf payoff hasn't been shown and the baseline is broken (§1).
- The classic path must also stay fully maintained in parallel, so this is two renderers forever.

## 4. Implementation: GPU side (shaders, draw pass)

### 4.1 [HIGH] Vertex shader does per-surface work per vertex, with many record fetches — verified
`levelmesh.vp main()` does, per vertex:
- 6 texels for the surface record;
- `LMFetchPlane` ×4, each calling `LMFetchSector`, which fetches 10 texels. The compiler may
  dead-code-eliminate unused lanes, but plane slots are needed for glow even on static surfaces;
- `LMFetchPlaneSector(planeRef[0])` twice more (light source, glow);
- `LMFetchSector(lightRef)`;
- `LMFetchLight` when light-listed.

That is **~40–70 texel fetches per vertex** before CSE, plus the full integer light chain, fog,
and glow. All of it is constant per surface and is recomputed for every vertex: 4× for walls,
N× for flat fans. Options:
- compute per-surface shading once per frame or on change (CPU dirty-driven, or a compute pass on
  Vulkan) into a small "resolved surface shading" record (1–2 texels), or
- fetch the surface/sector data in the fragment shader with a `flat` surface index, so it runs
  once per pixel rather than once per vertex. Fewer reads if the mesh is vertex-heavy, as myhouse is.

### 4.2 [HIGH] Per-surface constants interpolated as smooth varyings
`vLightLevel`, `vFogDensity`, `vFogColor`, `vLightFactor`, `vLightDist`, `vDesaturation`, and the 4
glow vec4s are per-surface constants, but they are declared smooth. That wastes interpolation
bandwidth and parameter-cache space. Declare them `flat`, or derive them in the FS from a `flat`
index.

### 4.3 [HIGH] Every level-geometry pixel runs a shader with `discard` — verified
The levelmesh effect deliberately drops `NO_ALPHATEST` (`hw_shaderpatcher.cpp:308-311`), and
effect shaders have no alpha-test-off variant. The opaque majority of the level is therefore shaded
by a program containing `discard` (`levelmesh.fp:948`). Many GPUs disable early-Z / Hi-Z for such
programs, so overdraw becomes full shading cost. Combined with §2.2 (no occlusion culling), this is
the worst case. Fix: two variants (opaque without `discard`, masked with it). Classic
`FShaderManager::Get(eff, alphateston, …)` already does this.

### 4.4 [HIGH] Draw submission per (region, texture) with VAO thrash — verified
`DrawLevelMesh` (`gl_framebuffer.cpp:487-517`) runs per entry:
- `GetGameTexture`,
- `SetRenderStyle`, `AlphaFunc`, `SetMaterial`, `SetTextureClamp`, `SetCulling`,
- `ApplyState` + `ApplyShader` (~30 uniform `Set` calls, including the `SetLevelMesh` param
  block on every apply, `gl_renderstate.cpp:130`),
- **two** `glBindVertexArray` calls (region VAO, then restore default; `gl_renderstate.cpp:448-460`),
- `glDrawElements`.

The list is ordered region-major, so the same texture is re-bound once per region. With the actual
partition (§5.1: ~one region per sector) this is roughly one draw per (sector, texture), which is
classic-scale draw counts with none of the classic's culling. Even with a correct partition, the
draw organization should be material-major across regions: one VBO + one shared IBO, so no VAO
switching. Even better, use `glMultiDrawElementsBaseVertex` (core GL 3.2) per material to merge
every visible range of a material into one call.

### 4.5 [HIGH] Clip distances not written; portal/mirror/split clipping broken — verified
`levelmesh.vp` never writes `gl_ClipDistance[]` or `ClipDistanceA/B`. `FGLRenderState` enables
`GL_CLIP_DISTANCE0..4` for portal clip lines/heights, translucent clip splits, and 3D-floor split
planes (`gl_renderstate.cpp:247-253, 528`). With a clip distance enabled and not written, results
are undefined, so mesh draws inside portal/mirror views can be clipped arbitrarily or not at all.
On `NO_CLIPDISTANCE_SUPPORT` hardware the FS reads unwritten varyings. Any view inside a portal is
affected today, because portal views reach `RenderScene` → `DrawLevelMesh`.

### 4.6 [MED] No normals
`aNormal` is unbound (`gl_levelmesh.cpp` header). `vEyeNormal`/`vWorldNormal` are effectively
zero, which affects:
- **SSAO:** with `gl_ssao`, the G-buffer normal output is wrong, so SSAO output is wrong;
- **dynamic lights (ticket 12) and normal/specular/PBR materials:** they need normals.

The normal can be derived per surface (line direction / plane normal) in the VS from records that
are already fetched.

### 4.7 [MED] Other GPU notes
- The LOD-free 32-bit IBOs and a 32-byte vertex are fine. But the pool keeps three CPU copies:
  - `FLevelMesh::vertices`,
  - `positions` (12 B/vert),
  - `FGLLevelMesh::mGpuPool`, which is never freed after upload.

  The raytrace adapter copies positions and indices again (`doom_levelmesh.cpp:27-46`). It also
  pushes one `MeshSurfaces` entry **per index**, not per triangle. Check that against what
  `VkRaytrace` expects.
- The sector ring texture buffer is `RGBA32F` with `GL_REPEAT` wrap params set on a buffer texture
  (ignored, harmless).
- `uSurfaceCount` is pushed but unused.

## 5. Implementation: CPU side (build, frame build)

### 5.1 [HIGH] Region flood-fill only traverses front→back — verified
`levelmesh.cpp:164-175`: `back = line->backsector`. When `cur` is the line's *back* sector,
`back == cur`, so the fill never crosses to the front sector. Regions fragment, which likely
explains "9,905 regions / 9,907 sectors" on SOS MAP32 (commit `1f7c6011` message). Consequences:
- one VAO + one IBO per region (≈10 k GL objects);
- per-region texRanges, so draw-count explosion (§4.4);
- the spec's "main region = component with player start" is meaningless. It isn't implemented
  anyway: the main region is simply region 0.

### 5.2 [HIGH] Quadratic load-time build — verified
- `BuildGeometry` (`levelmesh.cpp:1418-1446`): for each region, scan **all** segs and **all**
  subsectors. That is O(R × (segs + subsectors)).
- `BuildSubRanges` (`1459-1468`): for each region, scan **all** surfaces. That is O(R × surfaces).
  On SOS MAP32: 9,905 × 158,787 ≈ 1.6 × 10⁹ iterations, plus the same again for segs.
- Fix: bucket segs/subsectors/surfaces by region once (counting sort) and keep it linear. The
  per-texRange `TArray reordered` + copy per region is fine once it's linear.

### 5.3 [HIGH] Built and uploaded on every map load, even with `gl_uselevelmesh 0` — verified
`maploader.cpp:3260-3266` always builds `FLevelMesh`, the raytrace adapter, the sector ring, and
the GL upload (VBO, ~R VAOs/IBOs, three TBOs). That is a load-time and VRAM regression for every
classic-path user, and with §5.2 it is a severe one on big maps. Build it only when the levelmesh
path or the raytracer actually needs it.

### 5.4 [HIGH] 3D-light pack is O(L²) every frame — verified
`levelmesh_state.cpp:144-168` rebuilds the 3D-light buffer every frame. It dedups with
`lightSources.Contains(...)`, a linear scan of a `TArray`, and grows `lightData` with per-light
`Resize`. On myhouse MAP01 (9,812 3D floors, thousands of light entries) that is tens of millions
of pointer compares per frame, which likely costs more than the classic's entire 0.2 ms render
window (inferred; measure it). The dedup map is static topology: build it once at load
(`lightlistRef` already assumes stable indices) and only refresh `lightlevel`/colormap per frame.

### 5.5 [HIGH] Double pack + repack + full upload every frame — verified
For every sector, every frame:
1. `PackSnapshot` writes the 96 B record (virtual-ish accessors, colormap pack).
2. `RepackSectorSlot` memcpys it back out and expands it to 40 floats.
3. `glBufferSubData` uploads 160 B.

Three passes and 2.6× the bytes, all avoidable (§3.5, §3.6). The `HW_MAX_PIPELINE_BUFFERS` ring
inside one GL buffer doesn't help GL. `glBufferSubData` into a range the GPU may still be reading
can stall or force a driver-side copy.

### 5.6 [MED] Two cull walks per frame; the first is wasted and wrong — verified
The `D_Render` pre-cull (`d_main.cpp:621-623`):
- uses the player's mo position, not the camera;
- is non-interpolated;
- is fully redone in `RenderScene` (`hw_drawinfo.cpp:575-581`).

Each walk costs 8 SIMD mat-vec products per texRange. Delete the first walk.
`Build()` overwrites the shared per-level `levelMeshFrame` on every view (main, portals, camera
textures). That works only because each list is consumed immediately. It is incompatible with the
spec's slot/worker model.

### 5.7 [MED] Cull test details
- **The z-extrusion is too loose:** ±32768 is far wider than needed. Per-texRange or per-chunk
  real z bounds (min/max over the plane range of member sectors, widened for dynamic sectors)
  would make the test useful vertically.
- **The 8-corner clip-space test** is conservative and correct, but ~8× the cost of a
  center-extent vs 6 planes test. That doesn't matter at current texRange counts, but it will with
  real chunking.

### 5.8 [LOW] Misc
- **Stale slot:** on non-interpolated renders (`interpolate == false`), no pack/upload happens,
  but `DrawLevelMesh` still draws with the previous `currentSlot`. That is stale sector state for
  wipes, savegame pics, and camera textures rendered outside `D_Render`.
- **Placeholder bands:** `BuildBands` pushes dummy bands (`modelSector = 0`), so the band table is
  a placeholder.
- **Duplicate source of truth:** flags duplicated between `levelmesh.h` and `levelmesh.vp`
  `#define`s, with no static check tying them together. Same for the `LEVEL*` flag bit values
  hard-coded in the VS (one set was already wrong once, per the session-4 log).

## 6. Re-architecture options

Ordered by risk. All of them start with §7's measurements.

### Option A — "BSP visibility, static geometry" (lowest risk, likely biggest near-term win)
- **What stays:** the classic BSP walk + clipper, *only* to decide visibility. It already produces
  exposure flags, dither, portal registration, sky portals, sprite lists, and hack fills, so
  tickets 06/07/08's parity problems largely disappear.
- **What goes:** `HWWall::Process`/`HWFlat` work, per-wall vertex generation, and per-wall draws
  for static surfaces. Instead, each visible seg/subsector appends its **precomputed** static IBO
  ranges (baked at load by the classic emitter, §3.2) into a per-frame, per-material index list.
  That list is drawn with one `glMultiDrawElements` per material (GL 3.2 core) or a dynamic IBO.
- **Lighting:** per-surface resolved records, updated on change (§4.1).
- **Cost model:** the BSP walk stays. Wall setup, vertex generation, light-list building for
  unlit walls, and thousands of draw calls go away. GPU work stays proportional to the *visible*
  set.
- **Parity:** geometry and visibility identical by construction.

### Option B — GPU-driven (highest ceiling; Vulkan + GL 4.6 only)
- Spatial clusters (BSP-subtree or fixed-size meshlets with 3D AABBs), compute culling (frustum +
  Hi-Z from the previous frame's depth, two-pass), multi-draw-indirect, and bindless / descriptor
  indexing for textures.
- That gives O(1) CPU per frame, independent of level size. Portals become stencil passes over
  the same cluster set with per-view culling.
- GL33 stays on the classic path. This is where "vastly" faster becomes realistic on
  myhouse-class maps.

### Option C — the current spec, repaired
Required changes:
- spatial chunking separated from portal regions;
- occlusion (Hi-Z or BSP-coarse);
- removal of the classic walk, which requires every overlay feature (sky, translucent, polyobjects,
  hack fills, sprites, decals, exposure, dither) to be moved first;
- integer records, dirty uploads, flat varyings, opaque/masked variants, clip distances,
  material-major batching.

This keeps all of today's complexity (render worker, query prediction, re-bake lifecycle) and has
the longest path to any measurable win. Not recommended unless §7 shows the GPU brute-force draw
is cheap at scale.

Common to all options:
- drop ADR 0003's full copy in favor of dirty updates;
- drop the re-bake lifecycle (§3.4);
- move shading from per-vertex to per-surface-resolved;
- replace the forked shaders with variant axes;
- don't build on the classic path (§5.3).
